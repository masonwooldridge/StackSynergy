# Continuous deck assistant

The repeated-shortlist defect was reproduced through the actual chat API using a mock provider: an initial upgrade followed by “Other options, not that” selected the same addition. The server rebuilt the shortlist from the latest sentence without tracking prior suggestions/rejections. The UI held history only in component memory, cleared it on deck switching, stopped after12messages and sent no structured review outcome. Prior turns were already sent during one short mounted conversation; it was not a total absence of history from the model.

The assistant now retains separate owner/scope/deck (or commander idea) threads in browser-tab session storage through reloads and deck switching. Budget, bracket and ownership controls are retained per thread. This is tab-session persistence, not cloud sync or permanent browser history. Pending reviews become stale after reload and require a fresh request; no old review is silently applied. Storage failure leaves the thread in memory with a visible notice. New conversation explicitly clears the selected thread.

All submitted turns, including historical review states and referenced card names, reach the provider in order, alongside freshly verified deck membership. Historical card references are reverified by canonical ID, at most8additional cards; unavailable facts are flagged. Review metadata is not authority to mutate a deck. Applied review history remains historical if a later deck Undo restores cards. Chat-only “undo that” explains the workspace action without claiming a mutation or invoking the model.

Alternative requests remove prior additions from the eligible recommendation pool before ranking. Explicit rejection persists into later turns; named reconsideration and discussion of an earlier card remain allowed. “Cheaper” requires a lower verified card price than the previous suggested addition while retaining purchase budget and other constraints. If no new eligible option remains, the assistant explains the exhausted verified pool without another provider call or broadening the request. “Why” and comparison follow-ups use discussion mode with no swap queue. The prior substantive goal carries forward with the latest follow-up, while the constraint parser processes every user turn, including corrections.

The bound is80messages,2,000characters per transmitted message and100,000total context characters. Prior assistant prose may be clipped after review/reference metadata; user input is already limited to2,000characters. Older user constraints are not silently dropped by a sliding window. The thread/context guard stops before provider use and asks for a new conversation/restated goals when full. Existing3/minute,10/server/day, budget-ledger guards, legality/protected-card/role checks, grounded facts, stale-review checks and membership rules remain. All8paid attempts remain exhausted.
